# Instamart Customer Intelligence & Support Copilot

## Overview

A reproducible, offline capstone implementation using deterministic synthetic data. It combines a pandas cleaning pipeline and SQLite analytics, RFM clustering and lapse prediction, privacy-safe ticket triage, TF-IDF policy retrieval, and a tool-using refund agent. All LLM-style calls use the supplied `mock_llm.py`; no network or API key is required. All currency is INR.

## Reproduce

Run from the repository root with Python 3.11 or newer. On Windows, replace `source .venv/bin/activate` with `.venv\Scripts\activate`.

1. `python -m venv .venv`
2. `source .venv/bin/activate`
3. `python -m pip install --upgrade pip`
4. `python -m pip install -r requirements.txt`
5. `python generate_data.py`
6. `python pipeline.py A`
7. `python pipeline.py B`
8. `python pipeline.py C`
9. `python pipeline.py D`

`generate_data.py` and `mock_llm.py` are included as supplied in the brief. The generated raw data is deterministic. `pipeline.py all` runs the same stages in order. The pipeline creates the clean CSV files, SQLite database, SQL queries, model outputs, triage outputs, agent logs and state checkpoints.

Cleaning rules, applied in order:

- Customers: trim city values and apply title case; map gender variants to `male`, `female`, or `unknown`; coerce ages to numeric and make values outside 10–100 missing; fill missing ages using the city median via `groupby(...).transform`; parse signup dates.
- Orders: parse timestamps; remove exact duplicate rows; sort by timestamp and retain the latest record per order ID (this removes the earlier `pending` record); coerce amount to numeric and calculate missing values as rounded product price × quantity × (1 − discount/100); turn negative delivery durations into missing; fill missing completed-order durations with the median for that product category among completed orders; retain missing durations for cancelled orders.
- Products are stored without transformation. The clean CSVs and SQLite tables use the names required by the brief.

Validation output: `ALL CHECKPOINTS PASSED`. Cleaned orders: 12,309 unique orders, 11,110 completed and 1,199 cancelled; completed revenue is INR 2,998,668.80. No completed order has a missing delivery duration; cancelled orders retain missing delivery duration.

### Lapse model

The cutoff is `2025-09-01`; features use only pre-cutoff orders. The cohort has 1,156 customers and 443 lapsed customers (38.32%). A stratified 80/20 split produces 924 training and 232 test rows. The always-not-lapsed baseline has 61.6% accuracy and lapsed-class F1 of 0. Encoder and scaler are inside the pipeline and are fitted only on training rows; no resampler sees test rows. No order dated 2025-09-01 or later enters model features, and the RFM segment labels are not model features. The learned scaler frequency mean differs from the full-cohort mean because the scaler is fitted on training rows only.

Grid search results and untouched test evaluation:

| Model | Best parameters | CV F1 | Test confusion matrix (TN, FP / FN, TP) | Precision | Recall | F1 |
|---|---|---:|---|---:|---:|---:|
| Logistic regression | C=10 | 0.656 | [[104, 39], [32, 57]] | 0.594 | 0.640 | 0.616 |
| Random forest | max_depth=8, min_samples_leaf=10 | 0.686 | [[112, 31], [31, 58]] | 0.652 | 0.652 | 0.652 |

Random forest is selected because its test F1 is higher and it has a better precision/recall balance. Missing a genuinely lapsing customer loses a retention opportunity; incorrectly targeting a loyal customer wastes discounts and outreach effort. The class-balanced logistic experiment raises recall to 0.876 from 0.640, while precision is approximately 0.595 versus 0.594 and F1 rises to 0.709. The recall increase means more potentially lapsing customers are caught, at the cost of more false-positive outreach.

The chosen model is saved to `outputs/lapse_model.joblib` and reload predictions are asserted identical. `outputs/retention_list.csv` ranks Premium-segment test customers by predicted lapse probability. The Premium flag is based on whole-window RFM and includes September information, so this retention list is illustrative and is not a leakage-free evaluation. The top-10 list contains 0 actually lapsed customers in this run.

## Part C

### Privacy, guardrails and model output validation

The pipeline processes tickets in file order. Four empty tickets are skipped and four long tickets (734 estimated tokens) are flagged without a model call. Before model calls, it applies the required email, phone and order-ID patterns in order; the run redacts 55 emails, 91 phone numbers and 132 order IDs (278 total), and asserts no match remains in the redacted text. The model user message contains only the redacted ticket text.

Each model call has up to three retries with exponential backoff and jitter. `mock_llm.reset()` runs before each independent full run. In the full runs, all 19 transient failures are recovered. Valid JSON with an allowed category becomes `classified_json`; non-JSON replies are checked with lowercase `re.findall(r"[a-z]+", ...)` and accepted only when exactly one allowed category is found; all other outputs are sent to human review.

| Prompt | Classified tickets | Accuracy among classified | Total tokens | Tokens / classified ticket |
|---|---:|---:|---:|---:|
| Zero-shot | 147 | 85.7% (126/147) | 9,400 | 63.95 |
| Few-shot | 147 | 100% (147/147) | 10,960 | 74.56 |

The few-shot prompt costs 10.61 additional tokens per classified ticket on average, but improves accuracy by 14.3 percentage points in this deterministic evaluation, so the extra prompt cost is worthwhile when avoiding misrouted fraud or technical tickets matters. In the zero-shot confusion table, 11 fraud tickets and 10 technical tickets are incorrectly predicted as billing; other classified categories are correct.

The budget demonstration uses TOKEN_BUDGET=6,000 and ends with 56 tickets marked `budget_exhausted` (the accumulated usage can pass the limit on the call that takes it over; later calls stop). `outputs/triage_results.csv` is the full-budget few-shot output. ## Part D

### Policy retrieval and grounding

The five policy documents are chunked into 15 chunks using 40-word chunks with 10-word overlap: refund 4, delivery 3, escalation 3, payment 3, privacy 2. `TfidfVectorizer` is fitted on those chunks and cosine similarity ranks retrieval results. TF measures a term's frequency within a chunk; IDF gives greater weight to terms that are uncommon across chunks. TF-IDF is lexical and can miss semantically equivalent questions phrased with different words.

| Chunking | Expected source in top 3 (answerable) | Expected fact in answer (answerable) | Correct fallback (unanswerable) |
|---|---:|---:|---:|
| 40 words, overlap 10 | 12/12 | 12/12 | 2/2 |
| 40 words, overlap 0 | 12/12 | 10/12 | 2/2 |

With zero overlap, some expected facts are split across chunk boundaries and the answer model receives only partial policy text; two expected facts are missed. The answerer is instructed to use only retrieved context and to state when information is not found.

### Refund agent

The agent exposes five tools through `TOOLS_SPEC` and `TOOL_MAP`: `get_order`, `search_policy`, `calculate_refund`, `issue_refund`, and `escalate_to_human`. Only completed orders with delivery time over 45 minutes qualify; refunds over INR 1,000 are escalated instead of automatically issued. The simulated requests are assumed to be within the seven-day request window.

### ReAct versus plan-and-execute

ReAct uses several model calls for a typical workflow: S1 takes 5 calls, S5 takes 3, and S6 takes 2. A plan-and-execute approach can use one model call to create the plan and then execute deterministic tools, often reducing repeated prompt tokens when the plan is valid. However, ReAct conditions each next action on the actual observation: it can stop on `NOT_FOUND`, deny a cancelled order, or escalate a large refund instead of blindly executing later steps. For this refund workflow I would keep ReAct with strict iteration, token and timeout limits because financial actions need to respond to tool observations and have auditable checkpoints; a plan-and-execute variant could be added for low-risk lookup-only tasks.

## Limitations and Next Steps

- The dataset and policies are synthetic and do not represent real Instamart customer data or business rules.
- `mock_llm.py` is a deterministic test double, not a real language model; performance does not establish production model quality.
- The retention list is illustrative and not a leakage-free evaluation because its Premium flag comes from whole-window RFM, which includes September data. The model's own features still use only pre-cutoff orders.
- The implementation uses a small, fixed policy corpus and lexical TF-IDF retrieval. Production work should add versioned policies, stronger semantic retrieval, human approval and audit controls.
- Before production use, add tests for schema drift, transaction idempotency, authorization, monitoring, model drift, and operational failure recovery.
